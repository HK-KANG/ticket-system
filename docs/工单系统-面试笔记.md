## 1. SSM → Spring Boot 3 迁移对照

你 7 年的经验是 `Spring + SpringMVC + MyBatis + Vue + MySQL`，这一节把"旧经验"翻译成"现在岗位要的语言"。

| 你的旧项目 | 空窗期项目 | 差异点（要能讲） |

| `web.xml` + `spring-*.xml` 手写配置 | Spring Boot 自动配置 + yml | 自动配置原理、条件装配、starter |

## 2. 四个必背答话

### ① Spring Boot 自动配置原理

> `@SpringBootApplication` 里有 `@EnableAutoConfiguration`，它通过 `AutoConfigurationImportSelector` 读取 classpath 下所有 jar 里的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，收集候选配置类，再用 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 这类条件注解按需装配。
> 本质上就是把我以前在 XML 里手写的东西，变成了按条件自动注册的 Bean。

**追问准备**："为什么要有 `@ConditionalOnMissingBean`？" → 允许用户自定义覆盖默认配置，这是 starter 能被复用的前提。

### ② @Transactional 什么情况下会失效

四条标准答案：
1. 同一个类内部方法自调用（不走代理）
2. 方法不是 `public`
3. 异常被自己 catch 掉了
4. 抛的是受检异常（默认只回滚 `RuntimeException` 和 `Error`）

规避方式：拆成独立 Bean 调用，或 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` 手动标记回滚。

**加分**：还可以补"类没被 Spring 管理""数据库引擎不支持事务（MyISAM）"。

### ③ 为什么不用微服务

> 我的体量是单表 30 万、峰值几十 QPS。上微服务要付分布式事务、链路追踪、运维成本，换来的只有"看起来先进"。
> 但我做了 **3 实例部署**——那才是分布式真正会咬人的地方：定时任务会重复执行。我专门验证过，用 Redis 锁加按 id 分片解决，日志留在 `docs/sla-multi-instance.md` 里。

**这段的关键**：承认"不需要微服务"，同时证明"我知道分布式会出什么问题"。**这比硬吹微服务强十倍。**

### ④ Vue 是你写的还是后端兼的

> 直说前后端都做过。然后把 Vue2 → Vue3 的迁移讲出来：组合式 API 与 `setup`、`ref` 需要 `.value`、Pinia 取代 Vuex、Vite 取代 webpack（冷启动从分钟级到秒级）。

## 3. 选型答辩（版本问题，答不好比用旧版本更扣分）

> ⚠ 原任务书里有两句话不要照背：
> · "JDK 21 占 40%"——这是未经核实的数字，面试官追问"哪来的"你答不上
> · "Spring Boot 3.5 在 2026-06 已结束开源支持"——这句话本身有争议，而且说了等于自己给自己挖坑
> 用下面这版。

**① 为什么用 JDK 21 不追更新版本？**
> 21 是目前的 LTS，生态兼容性最稳，虚拟线程也是在这个版本正式落地的。对我来说，语言版本不是我项目的价值所在，稳定能交付优先。

**② 为什么用 Spring Boot 3.5 不用 4.x？**
> 3.5 是 3.x 的最后一版，MyBatis-Plus、Knife4j 这条链在 3.x 上验证最充分。4.x 迁到了 Spring Framework 7，生态跟进需要时间。这个体量的项目，稳定比尝鲜重要。如果这是公司生产系统，我会把升级排进季度计划而不是现在做。

**③ 为什么单体不用微服务？** → 见第 2 节 ③

**④ 为什么用 Redis 而不是本地缓存？**
> 我要跑 3 实例，本地缓存各存各的，会出现数据不一致。而且分布式锁、限流这些必须要一个集中的地方。

## 5. 这个项目能讲的东西：三个故事

面试官一般只深挖 1-2 个点，准备三个就够，每个能讲 3 分钟。

### 故事 1：抢单的两种实现（并发）
- 背景：20 个坐席同时抢一张单
- 版本 A：`UPDATE ... WHERE status='PENDING' AND version=?`，靠行锁 + 版本号
- 版本 B：Redis 分布式锁 `SETNX` + Lua 释放
- 结果：两个版本成功数都严格 = 1；但 A 的 DB UPDATE 执行了 20 次，B 只执行 1 次
- 结论：低并发用乐观锁更简单；高并发下乐观锁失败率高、白白打 DB，才值得上分布式锁
- **数字必须是你自己跑出来的，写在 `docs/concurrency-compare.md` 里**

### 故事 2：深翻页优化（SQL）
- 基线：offset 翻到第 5000 页时 P99 = X ms
- 手段：延迟关联（先查主键再回表）→ 游标分页（`WHERE id > lastId`）
- 结果：P99 降到 Y ms，下降 Z%
- 加分：能拿出 EXPLAIN 前后对比图

### 故事 3：3 实例下定时任务只执行一次（分布式）
- 问题：`docker compose up --scale app=3` 后，每个实例都在跑 SLA 扫描，工单被升级 3 次
- 解法：Redis 锁 + 按 id 取模分片 + 数据库条件更新兜底
- 验证：3 实例跑 10 分钟，一条超时工单只产生 1 条 dispatch 记录

## 7. 虚拟线程：这是你最能加分也最容易讲错的一点

如果 Phase 6 的第 ⑥ 项做完了，这个点的深度超过 90% 的候选人。

**正确的讲法**：
> 虚拟线程解决的是"线程等待 IO 时占着平台线程"的问题，所以它只对 **IO 等待型**场景有效——查库、调外部接口。CPU 密集型场景没有提升，因为没有等待可省。

**必须知道的坑（面试官会追问）**：
> JDK 21 里，`synchronized` 块会把虚拟线程 **pin** 在载体线程上，等于失去了虚拟线程的意义。这是 JEP 491 在 JDK 24 才修的。
> 我压测时就踩过：热点方法里有一个 `synchronized`，测出来虚拟线程和平台线程几乎没差别；换成 `ReentrantLock` 之后才有提升。
> 排查方式是加 `-Djdk.tracePinnedThreads=full` 启动参数，会打印出被 pin 住的栈。

**这段一旦讲出来，对方会知道你真的跑过，不是看文章。**

⚠ 前提：你真的做了这个实验。没做就说"我了解原理，但没有实测"。
