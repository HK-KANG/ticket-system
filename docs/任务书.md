# 售后工单系统 · Hermes 开发任务书

> 用法：Hermes 在本机直接读盘跑命令，不需要你复制粘贴内容。**一次只做一个 Phase**：先让它输出执行计划，你确认后再写代码。每个 Phase 结束，按「验收标准」逐条验证，不通过不进下一阶段。

---

## 0. 全局约束（每个 Phase 开头都要带上这段）

```
【项目】售后工单处理系统（单体 Spring Boot 应用，个人作品集项目）
【硬约束】
1. 单体应用，不拆微服务，不引入 Spring Cloud、Nacos、Sentinel
2. JDK 21 + Spring Boot 3.5.16 + MyBatis-Plus 3.5.x + MySQL 8.4 + Redis 8.2 + RabbitMQ 4.2
3. 代码版本管理用 Git（GitHub 仓库），禁止使用 SVN；每天至少 1 次有意义的 commit
4. 所有 SQL 必须走 MyBatis-Plus 或 XML，禁止在 Service 层拼接 SQL 字符串
4. 所有接口返回统一 Result<T> 结构：code / message / data / traceId
5. 所有表必须有 create_time、update_time、deleted（逻辑删除）
6. 每个接口必须有参数校验（Jakarta Validation）
7. 不允许使用任何需要联网注册的第三方服务（AI 分类除外，走 DeepSeek HTTP API）
8. 不引入 Elasticsearch、Milvus、ShardingSphere 等重型组件
9. 每个类、每个公开方法必须有中文注释，说明职责
10. 禁止生成"示例/演示用的假数据初始化代码"，数据由独立脚本生成
【代码风格】
- 分层：controller / service / mapper / entity / dto / vo / config / common / job
- Controller 只做参数校验和调用，不写业务逻辑
- Service 方法命名体现业务动作：createTicket / acceptTicket / transferTicket
```

# 一、页面与模块清单（先定页面，再定接口）

> 这份清单的作用：**页面决定接口，接口决定后端**。先把它写死，AI 才不会随口生成一堆用不上的接口，也不会漏掉前端要用的字段。

## 1.1 前端技术约束（凡是涉及前端的 Phase 都带上这段）

```
【前端约束】
1. Vue3 + Vite + Element Plus + Pinia + axios 封装，单页应用（SPA）
2. 只做 PC 端，1280px 宽度可用即可，不做移动端适配、不做复杂动效
3. 只实现下面清单里的页面，一个都不许多加，也不许少做
4. 每个页面必须正确处理三种状态：空数据、接口报错、长列表分页
5. 所有列表页统一用 Element Plus 的 Table + Pagination，查询条件放 SearchForm
6. 请求统一走封装好的 request.js（带 token、带 traceId、统一错误提示）
7. 权限按角色渲染：没权限的菜单不显示，直接访问路由要拦到 403 页
```

## 1.4 若时间紧，只做这 5 个 P0 页面

`B1 抢单大厅` → `B3 工单处理页` → `C2 工单总览` → `C1 数据看板` → `C6 导出中心`

## 2.2 数据库：只用两个，别再加第三个

| 库 | 角色 | 存什么 | 关键配置 |
|---|---|---|---|
| **MySQL 8.4** | 业务主库 | 8 张业务表（工单、日志、派单、回复、SLA、用户、幂等、outbox） | InnoDB、`utf8mb4`、事务隔离 **RR**、开启慢查询日志（`slow_query_log=1`, `long_query_time=1`） |
| **Redis 8.2** | 缓存 + 协调 | 登录 token、工单详情缓存、分布式锁、令牌桶、导出进度、超时兜底扫描分片标记 | 不用做持久化策略设计，默认 RDB 即可 |

**明确不用**：Elasticsearch（30 万数据用不上，需要全文检索就用 Redis 8 内置的搜索能力，这本身就是个能讲的技术判断）、MongoDB、pgvector、ShardingSphere、Seata。

**你要能在面试说清的一句话**：「业务数据只有一类、量级 30 万、并发需求几十 QPS，所以一个 MySQL + 一个 Redis 足够。上 ES 是为了解决我没遇到的问题，那是负收益。」

## 2.3 代码管理：**用 Git，不用 SVN**

| 判断 | 说明 |
|---|---|
| **必须用 Git** | 招聘方默认 Git；简历写 SVN 会被判为"老环境"。GitHub 公开仓库是你**唯一能被验证的代码证据**。 |
| **为什么对空窗期尤其重要** | **提交时间戳的连续性**，是证明"这个项目你真的做了几个月、不是临时拼的"最有力的证据。面试官打开你的 commit 历史，看到连续 15 天每天都有提交，比任何话术都有效。 |
| 分支策略 | `main`（随时可运行）+ `feat/phase-0x-xxx` 功能分支，做完合并。有 PR 记录更好 |
| 提交规范 | 中文 commit message，写清"做了什么"：`feat: 完成抢单接口乐观锁版本`、`perf: 工单列表加联合索引，深翻页 P99 降至 45ms` |
| 每日节奏 | **每天至少 1 次有意义的 commit**，绝对禁止最后一次性导入所有代码 |
| 仓库结构 | `backend/` + `frontend/` + `docs/` + `docker/` 一个仓库，根目录 README 是门面 |

**如果面试被问"你以前公司用 SVN，Git 熟吗？"** 照这个答：
> "公司用 SVN，我自己的项目一直用 Git。两者的区别我清楚：SVN 是集中式，必须连服务器才能提交、分支成本高、靠 `.svn` 目录追踪；Git 是分布式，本地有完整历史，分支几乎零成本，所以更适合我这种按阶段迭代、要保留完整演进过程的项目。"

## 2.4 版本选定后，三条必须准备好的「选型答辩」

被问到版本问题时，答不好比用旧版本更扣分。

> **① 为什么 JDK 21 不用 25？** 21 是当前生产主流（占比 40%），生态兼容性最稳；25 是更新的 LTS，但我这个项目的价值不在语言版本上，稳定能交付优先。
>
> **② 为什么 Spring Boot 3.5 不用 4.x？** 我知道 3.5 在 2026-06 已结束开源支持。选它是因为 MyBatis-Plus、springdoc 这条链在 3.x 上验证最充分；4.x 要迁到 Spring Framework 7 / Jakarta EE 11，对这个体量的项目迁移收益不划算。如果这是公司生产系统，我会把升级排进季度计划。
>
> **③ 为什么单体不用微服务？** 我的量级是单表 30 万、峰值几十 QPS。上微服务要付分布式事务、链路追踪、运维成本，换来的只有"看起来先进"。但我做了 **3 实例部署**——那才是分布式真正会咬人的地方（定时任务重复执行），我专门验证过。

## 2.5 组件优先级：必须 / 最小版 / 可删（防止把工期耗在环境配置上）

> **给 Hermes 的硬要求**：本节标注「可删」的组件，配置超过 1 小时仍不通就**直接跳过，不要反复折腾**。工期是本项目最贵的资源，环境配置不是交付物。

### A. 必须做（不做项目立不住）

| 组件 | 学习/配置成本 | 为什么必须 | 最小实现要求 |
|---|---|---|---|
| **Redis** | 1 天 | 缓存 + 并发两块的载体 | 详情缓存、分布式锁、令牌桶，三个用法会写即可 |
| **RabbitMQ** | 0.5 天 | SLA 延迟升级、异步导出 | 只做两种用法：异步解耦 + TTL+死信延迟，**不学全套** |
| **JMeter（或 wrk）** | 0.5 天 | 没有压测数据，这个项目就白做 | 会发一个 HTTP 请求、设并发、看聚合报告 |
| **EXPLAIN + MySQL 慢日志** | 0.5 天 | 索引优化必须讲得清 | 看得懂 type / rows / key / Extra 四列 |
| **Logback + MDC（traceId）** | 30 分钟 | 性价比最高的加分项 | 一个 Filter 塞 traceId 进 MDC 并回传响应头 |
| **Jakarta Validation** | 30 分钟 | 等价于旧项目的 Hibernate Validator | 只用 `@NotNull/@Size/@Pattern` |
| **EasyExcel** | 1 小时 | Phase 7 防 OOM 的载体 | 分批查 + 分批写，不设计花活 |
| **Vue3 + Vite + Pinia** | 1 天 | 5 个 P0 页面要用 | Vite 就是 `npm run dev`；Pinia 比 Vuex 更简单 |

### B. 必须，但只用最小版

| 组件 | 最小版范围 | 成本 |
|---|---|---|
| **JWT + 拦截器** | 只做三件事：登录签 token → 拦截器校验 → 注解校验角色。**不做刷新令牌、不做多端互踢、不做复杂权限树** | 半天 |

# 三、SSM → Spring Boot 3 迁移对照（面试必备）

你的历史项目是 `Spring + SpringMVC + MyBatis + Vue + MySQL`（SSM），这一节把"旧经验"翻译成"现在岗位要的语言"。

## 3.1 对照表

| 你的旧项目 | 空窗期项目 | 差异点（要能讲） |
|---|---|---|
| `web.xml` + `spring-*.xml` 手写配置 | Spring Boot 自动配置 + `application.yml` | 自动配置原理、条件装配、starter 机制 |
| 外置 Tomcat 部署 war | 内嵌 Tomcat，打 fat jar | 为什么现在不用外置容器 |
| MyBatis XML 手写 SQL | MyBatis-Plus 条件构造 + XML 混合 | 你的 XML 功底是优势，别丢 |
| 无缓存 | Redis 缓存 + 分布式锁 + 限流 | Cache Aside、击穿/穿透/雪崩 |
| 无 MQ | RabbitMQ 异步 + 延迟队列 | 幂等消费、死信、延迟消息 |
| 单机部署 | Docker + 3 实例 | 多实例下定时任务防重 |
| 无压测 | JMeter + EXPLAIN + 慢日志 | 性能数据的来源 |
| Vue2 + webpack | Vue3 + Vite + Pinia | 组合式 API、`ref` 解包、构建提速 |

## 3.2 四个必背答话（SSM 出身最容易被问翻的）

**① "Spring Boot 自动配置原理讲一下"**
> `@SpringBootApplication` 里有 `@EnableAutoConfiguration`，它通过 `AutoConfigurationImportSelector` 读取 classpath 下所有 jar 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，收集配置类，再用 `@ConditionalOnClass`、`@ConditionalOnMissingBean` 这类条件注解按需装配。**本质上就是把我以前在 XML 里手写的东西，变成按条件自动注册的 Bean。**

**② "@Transactional 什么情况下会失效"**
> 四个标准答案：同类内部方法调用（不走代理）、方法不是 `public`、异常被自己 catch 掉、抛的是受检异常（默认只回滚 `RuntimeException`）。规避方式是拆成独立 Bean 调用，或用 `TransactionSynchronizationManager` 手动标记回滚。

**③ "你们为什么不用微服务"**
> 见 2.4 的第 ③ 条。要点：体量不够 + 但我用 3 实例验证过分布式真正的问题（定时任务重复执行）。

**④ "Vue 是你写的还是后端兼的"**
> 直说前后端都做过。然后把 Vue2 → Vue3 的迁移讲出来：组合式 API 与 `setup`、`ref` 需要 `.value`、Pinia 取代 Vuex、Vite 取代 webpack（冷启动从分钟级到秒级）。

## 3.3 旧经历在简历上怎么写

不要写：~~"使用 Spring、SpringMVC、MyBatis 开发 XX 管理系统，Vue 开发前端页面，MySQL 存储数据。"~~（会被直接判成老技术）

改成这样（内容真实，叙事不同）：

> **XX 管理系统（2021.06–2025.04）**
> 技术栈：Spring MVC + MyBatis + MySQL + Vue2
> - 独立完成后端 40+ 接口与前端 20+ 页面，覆盖 XX 业务全流程
> - 基于 MyBatis 动态 SQL 完成多表关联查询，针对慢查询做过索引与 SQL 改写，核心列表接口从 X s 降至 Y ms
> - 使用 `@Transactional` 管理跨表写操作，梳理事务边界，规避同类调用导致的代理失效
> - 2025 年起完成技术栈升级：Spring MVC → Spring Boot 3 / JDK 21，并以个人项目重构验证差异

**铁律**：不要写"高并发""亿级数据""分布式"——你那个体量一追问就穿。写"在这个体量下做到的最好"，安全且更有说服力。

## 给 Hermes 的用法纪律（重要）

1. **一个 Phase 一个会话**。做完一个 Phase 就 `/new`，别在一个会话里连推三个——上下文一长，它就开始忘掉前面的约定。
2. **开工先要计划**。第一句固定这么写：`先读 .hermes.md 和 docs/tasks.md 里的 Phase N，输出实现计划和要新建/修改的文件清单，等我确认再写代码。`
3. **必须带工作目录**。所有会话都在 `D:\projects\ticket-system` 下启动，否则 `.hermes.md` 不加载，下面的规矩全部失效。
4. **验收要真实输出**。每个 Phase 结束让它跑 `build.cmd -q -DskipTests package` 并实际启动，把终端原样输出贴出来。它说"应该能跑"不算通过。
5. **不许自己加依赖**。pom 里新增任何 starter 之前必须先问你，说清为什么加、替代方案是什么。
6. **改前先 commit**。每个 Phase 开始前 `git add -A && git commit -m "before phase N"`，出问题一把回滚；Phase 结束再 commit 一次。
7. **关键设计必须解释**。索引、锁、事务、缓存这四处，结尾固定加一句 `说明这个设计为什么这么做、替代方案是什么、为什么不选`——这些解释就是你面试的稿子。
8. **不许编数据**。压测数字、QPS、响应时间必须真跑出来。空窗期项目最怕"数据是编的"，一问细节就穿。
9. **看不懂就让它讲**。不要硬改。让它逐行解释，理解不了就重写那一段。

## 怎么在 Hermes 里跑一个 Phase（操作手册）

终端里：

```
cd /mnt/d/projects/ticket-system
hermes
```

**第一句（把 N 换成阶段号）：**

```
读 .hermes.md 和 docs/tasks.md 的 Phase N。先输出实现计划和要改的文件清单，不要写代码。
```

**你确认计划后：**

```
按计划执行。每改完一个文件跑一次 build.cmd -q -DskipTests compile，报错当场修，别攒着。
```

**收尾：**

```
跑 Phase N 验收清单里的每一条，把真实输出贴给我，然后 git commit。
```

跟 Cursor 时代最大的区别：**不用再复制粘贴文件内容**。Hermes 在你自己机器上直接读盘、直接跑命令，你只负责三件事——确认计划、看真实输出、判断业务对不对。
