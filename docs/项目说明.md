# 售后工单系统 · 项目说明

> 这份文档回答三个问题：这个项目是干什么的、由哪些模块组成、每个部分为什么这么设计。
> 写给两个人看：未来的你自己（两个月后还能快速捡起来），以及面试官（他要能听懂你在讲什么）。

---

## 一、一句话说明

一个**售后工单处理系统**：客户提交问题 → 系统按 SLA 规则限时 → 坐席抢单处理 → 超时自动升级 → 管理员看数据。

技术上是单体 Spring Boot 应用 + Vue3 前后端分离，一人可独立完成，但覆盖了后端开发面试要求的绝大部分知识点。

---

## 二、为什么做这个项目

不是为了上线赚钱，是为了**能讲清楚一个完整的后端系统**。

面试官问"你做过什么项目"时，最怕听到的是"我跟着教程做了个商城"。他真正想确认的是：

| 他想确认的事 | 这个项目怎么回答 |
|---|---|
| 你懂不懂并发 | 抢单用乐观锁，20 个坐席同时抢一单只能有一个成功 |
| 你懂不懂事务 | 创建工单要同时写主表、日志表、派单表，事务边界在哪 |
| 你懂不懂索引 | 13 个索引，每个都对应一个具体查询，能现场 EXPLAIN |
| 你懂不懂权限 | 三个角色，接口层用注解拦，不是只在前端藏按钮 |
| 你懂不懂异步 | 导出大文件用 RabbitMQ 排队，不阻塞请求 |
| 你懂不懂排查问题 | 每个请求带 traceId，日志能串起一次调用的全过程 |

所以这个项目的每个设计选择，背后都有一个"面试官会问什么"的答案。

## 三、业务场景（用一个人讲清楚）

张三在网上买了一个吹风机，用了三天坏了。他打开 APP 找到售后页面：

1. **提交工单**：填标题、选分类（质量问题）、选优先级、写描述
2. **系统处理**：自动生成单号 `TK202611060001`，按「质量问题 + P0」查 SLA 规则，
   规定 30 分钟内必须响应，于是算出截止时间 = 现在 + 30 分钟
3. **进入抢单池**：这单需要「售后一组」处理，出现在该组坐席的抢单大厅
4. **坐席抢单**：李四看到卡片，倒计时还剩 28 分钟，点抢单
   - 如果同时有另一个坐席也点了，数据库乐观锁会让他失败，提示"已被他人抢走"
5. **处理过程**：李四回复客户、写内部备注（客户看不到）、必要时转派给别的组
6. **超时升级**：如果 30 分钟内没人接，定时任务扫到超时，自动升级给上级组并标记
7. **关闭工单**：问题解决后状态走到「已解决」→「已关闭」，全程每一步都写进流转日志
8. **管理员**：看到全量工单、SLA 达成率、各分类分布，可以导出 Excel 交报表

## 四、三类角色与权限

| 角色 | 能做什么 | 看不到什么 |
|---|---|---|
| **CUSTOMER 客户** | 提交工单、查看**自己的**工单、补充说明 | 别人的工单、抢单池、任何统计数据 |
| **AGENT 坐席** | 抢本组的单、处理、回复、转派 | 别的组的单、客户信息全量、统计后台 |
| **ADMIN 管理员** | 看全量工单、看板、导出、用户列表 | —— |

关键点：**权限在接口层校验，不是前端藏菜单**。
前端不显示菜单只是体验，真正的防线是拦截器 + `@RequireRole` 注解。
客户直接拿 token 调管理员接口，会拿到 HTTP 403。

## 五、工单状态机

```
                  ┌──────────────────────────────┐
                  │                              │
  [创建] → PENDING ──抢单/派单──→ ASSIGNED ──接单──→ PROCESSING
   待派单                             已派单              处理中
                  │                                          │
                  └──超时──→ ESCALATED                       │
                             已升级                          │
                                                             ↓
                                        CLOSED ←──── RESOLVED
                                        已关闭          已解决
```

允许的跳转（不允许的一律拒绝，不是"能改就改"）：

| 从 | 到 | 谁可以 |
|---|---|---|
| PENDING | ASSIGNED | 坐席抢单 / 管理员派单 |
| ASSIGNED | PROCESSING | 该工单的处理人 |
| PROCESSING | RESOLVED | 该工单的处理人 |
| RESOLVED | CLOSED | 客户确认 / 管理员关闭 |
| PENDING / ASSIGNED | ESCALATED | 系统（超时任务） |

状态机写在 Service 里，用一张 map 定义合法跳转，非法跳转抛业务异常——这样以后加工单状态只需要改一处。

## 七、数据模型（7 张表）

| 表 | 一句话职责 |
|---|---|
| `t_user` | 用户和坐席。一个账号靠 role 区分三种身份，坐席带技能组和最大在办数 |
| `t_ticket` | 工单主表。全系统核心，状态、处理人、SLA 截止时间、乐观锁版本号都在这 |
| `t_ticket_log` | 流转日志。每次状态变化写一条，详情页的"进度时间线"就是它 |
| `t_ticket_dispatch` | 派单记录。记录工单在坐席之间怎么流转的，用于算转派率 |
| `t_ticket_comment` | 回复记录。`is_internal=1` 是坐席内部备注，客户侧接口必须过滤 |
| `t_sla_rule` | SLA 规则。分类 + 优先级唯一命中一条，决定这张单多久必须响应 |
| `t_idempotent` | 幂等表。靠唯一索引拦截重复提交，网络抖动重复点击不会建出两张单 |

设计上的三个取舍（面试会问）：

1. **流水表不加 update_time 和 deleted**
   日志、派单、回复是只增不改的事实记录，加了这两个字段永远用不上，还会引入"这条日志算不算被删了"的歧义。

2. **不建物理外键**
   关联由应用层保证。物理外键在批量归档、分库分表时会成为枷锁，互联网公司普遍这么选。

3. **幂等靠数据库唯一索引，不靠 Redis**
   "先查后插"存在并发竞态，两个线程可能同时判断"不存在"。只有数据库唯一索引能真正保证唯一。

## 八、技术架构

```
浏览器 (Vue3 + Element Plus)
   │  axios，自动带 token 和 traceId
   ▼
Vite 开发服务器 5173  ──/api 代理──▶  Spring Boot 8080
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
                 MySQL 8.4           Redis 8            RabbitMQ 4
              业务数据+流水        令牌、缓存、        通知、延迟队列、
                                 分布式锁、限流        导出任务
```

后端分层（严格单向依赖，Controller 不碰数据库）：

```
controller  只做参数校验 + 调用 service，不写业务逻辑
   ↓
service     业务规则、事务边界、状态流转
   ↓
mapper      MyBatis-Plus，只做数据访问
   ↓
entity      与表结构一一对应
```

另有 dto（接收前端参数）、vo（返回给前端）、common（Result/异常/常量）、config、security、job（定时任务）。

## 九、技术亮点（面试可讲，标注实现状态）

| 亮点 | 做法 | 状态 |
|---|---|---|
| JWT + Redis 可撤销 | 纯 JWT 签出去收不回来，存一份到 Redis 才能踢下线 | ✅ |
| 乐观锁抢单 | `UPDATE ... WHERE id=? AND version=?`，影响行数为 0 即抢失败 | ✅ 20 并发实测只有 1 人成功 |
| Redis 分布式锁（对比版） | SETNX + 30s 过期 + Lua 比对释放 | ✅ 已实现但生产不用，见 `docs/concurrency-compare.md` |
| 自动派单 | 同技能组在线坐席按在办数升序，超过 max_load 跳过 | ✅ |
| 幂等防重复提交 | 客户端传 requestId，数据库唯一索引兜底 | ✅ 实测 5 连发只建 1 条 |
| 状态机 | 合法流转集中定义在枚举里，非法跳转抛业务异常 | ✅ 待派单不能直接关闭 |
| 单号生成 | Redis INCR 原子自增，按天分 key + 48h TTL，Redis 故障降级时间戳 | ✅ |
| 全链路 traceId | 过滤器写入 MDC，日志和响应头一致 | ✅ |
| 越权返回 404 | 不泄露"存在但无权看" | ✅ |
| 逻辑删除 | `deleted` 字段 + MyBatis-Plus 自动拼条件 | ✅ |
| SLA 超时扫描 | 定时任务扫 `sla_deadline < now`，配合 RabbitMQ 延迟队列 | ✅ 延迟消息 + 扫描兜底，三实例实测只升一次 |
| 异步导出 | 请求只建任务返回，RabbitMQ 排队后台生成 Excel，前端轮询进度 | ✅ 实测 2.99 万行 2.09MB，分批 2000 流式写 |
| 深分页优化 | 游标分页 + (create_time,id) 索引；offset 深翻页实测无解 | ✅ 34.2ms → 4.31ms |

## 十一、面试官最可能追问的八个问题

1. **为什么用 JWT 还存 Redis？**
   JWT 无状态签出去收不回来，存 Redis 是为了支持踢下线和重新登录后旧令牌立即失效。代价是每次请求多一次 Redis 读。

2. **抢单怎么防止超卖？**
   乐观锁。`version` 字段，UPDATE 时带上旧版本号，影响行数为 0 说明被别人抢先，据此返回失败。不用悲观锁是因为抢单冲突概率低、持锁时间短。

3. **创建工单涉及几张表？事务怎么控制？**
   主表 + 日志表（+ 幂等表）。三步在一个 `@Transactional` 方法里，任何一步失败整体回滚。

4. **索引为什么这么建？**
   每条索引对应一个真实查询。比如抢单大厅 `WHERE skill_group=? AND status='PENDING' ORDER BY create_time DESC`，所以建 `(skill_group, status, create_time)`，字段顺序 = 过滤 + 排序，避免 filesort。

5. **客户怎么保证只能看到自己的工单？**
   不是在 Controller 里接收 creatorId 参数（那样能被伪造），而是从 token 解析出 userId 后强制拼进查询条件。

6. **重复提交两次会建两张单吗？**
   不会。前端带 requestId，服务端用 `biz_type + requestId` 插幂等表，唯一索引冲突即判定重复，直接返回首次结果。

7. **导出十万条工单会卡住接口吗？**
   不会。请求只创建任务记录并投递 MQ，消费者分批查库写 Excel，前端轮询进度。

8. **线上出问题你怎么查？**
   每个请求有 traceId，响应头返回给前端（用户截图就能提供），后端日志用 `%X{traceId}` 输出，按 ID grep 一次调用的全链路。
