## A. 开场类（几乎必问，3 分钟定印象）

### A1. 介绍一下这个项目

**答**：这是一个售后工单系统，解决的是"客户买了东西出问题，怎么在承诺时间内处理完"。
三个角色：客户提交工单，坐席抢单处理，管理员看数据。

技术上是前后端分离，后端 Spring Boot 3 单体，MySQL + Redis，前端 Vue 3。

我做这个项目主要是想把它当成一个能讲清楚的作品：不只是增删改查，
还包括了 JWT + Redis 的可撤销登录态、接口幂等、状态机、乐观锁并发抢单，
以及 13 个索引的设计依据。整套接口有自动化验收脚本，抢单做过 20 并发对比实验。

**注意**：不要背功能列表，说"解决什么问题"+"我特意练了什么"。

### A2. 这个项目里你负责哪部分？

**答**：全栈独立开发，从建表到前端页面都是我自己做的。
不过我要说清楚哪些是我真正想明白的、哪些是照着文档写的——
并发抢单和索引这两块我做过实测，可以深入聊；前端部分我是够用水平，
Vue 的响应式和路由守卫我能改能调，但不会说自己精通。

**为什么这么答**：主动划边界比硬撑更可信。面试官最怕"什么都精通"的候选人。

### A3. 项目里最难的地方是什么？

**答**：抢单的并发。一开始我以为加个 `synchronized` 就行，
后来意识到多实例部署时进程锁没用，才去查了乐观锁和分布式锁两条路。

最后两个版本都实现了：数据库乐观锁（`WHERE version=?`，影响行数为 0 就说明被别人抢了）
和 Redis 分布式锁（SETNX + 30 秒过期 + Lua 释放）。

20 个并发打同一张单，两个版本都是只有 1 个人成功。
但生产上我用乐观锁——竞争只在一行数据上，数据库行锁够用，
还能少一个必须存活的 Redis 依赖。

**追问预备**：为什么不用悲观锁 → 见 D2。

### A4. 如果让你重做一次，会改什么？

**答**：三件事。

一是我会把"状态流转"做成配置或者数据库表，而不是写死在枚举里。
现在 6 个状态、13 条合法流转，改一次要改代码重新发版；真实业务里状态经常变。

二是补单元测试。我现在只有接口级验收脚本（29 项断言），能证明功能对，
但没法证明"某段逻辑在边界条件下也对"。比如 SLA 计算里如果规则缺失会返回 null，
这个分支只有代码注释，没有测试覆盖。

三是前端会用 TypeScript。现在字段名写错只有运行时才发现。

**为什么这么答**：能自己指出问题，说明你真在做工程而不是拼 demo。

### A5. 这个项目上线过吗？有多少用户？

**答**：没有上线，是个人项目。我在本地跑通了完整流程，用 Docker 起中间件，
接口有验收脚本，并发做过压测。

我不敢说它扛得住真实流量——压测是在本机、20 并发、单实例，

## B. 需求与数据建模

### B1. 为什么是 7 张表？怎么划分的？

**答**：按"主体 / 事实 / 配置"分三类。

主体表：用户、工单。
事实流水表：流转日志、派单记录、回复——都是只增不改的记录。
配置表：SLA 规则。
还有一张辅助表：幂等记录。

7 张：`t_user`、`t_ticket`、`t_ticket_log`、`t_ticket_dispatch`、`t_ticket_comment`、
`t_sla_rule`、`t_idempotent`。

**关键点**：工单主表只存"当前状态"，历史全在日志表。
这样主表字段不会随流转膨胀，日志表又能完整回放。

### B2. 流水表为什么没有 `update_time` 和 `deleted`？

**答**：因为它们是**只增不改的事实记录**。

`t_ticket_log` 记的是"某时刻状态从 A 变成 B"，这条事实不会变。
加 `update_time` 结果永远等于 `create_time`，是冗余字段；
加 `deleted` 更糟——日志被删了，"谁改过这张单"就说不清了，
审计价值直接归零。

主表 `t_ticket` 有 `update_time` 和 `deleted`，因为工单会被修改、需要软删除。

**这题能看出你是否理解"表和表的性质不同"，不是所有表都套同一模板。**

### B3. 为什么不建物理外键？

**答**：三个原因。

一是分库分表。外键跨库没法建，现在不建以后好迁。
二是批量操作。删一个用户要级联，外键会锁住相关行，批量导入也慢。
三是互联网惯例：关联由应用层保证，配合索引和事务。

代价我也清楚：数据可能不一致（比如日志表引用了不存在的工单）。
我的缓解办法是——所有关联写入都在同一个 `@Transactional` 里，
并且列表查询不用 JOIN，而是**先查工单列表，再 `selectBatchIds` 批量取用户，
在内存里拼 creatorName / handlerName**。

**为什么不用 JOIN**（这其实是主动选择，不是偷懒）：
一是避免 N+1（如果循环里查用户就是 N 次查询，我一次批量取完）；
二是不依赖外键也能算关联，表结构解耦，以后工单表分库时不用改查询。

代价是两次查询 + 一次内存映射。数据量小的列表页完全够用。

⚠️ **弱点**：我没有真的写过数据一致性校验任务。如果被追问
"你怎么知道现在数据是一致的"，诚实答"目前只能靠代码约定，没做定期校验"。

### B4. 状态机是怎么实现的？

**答**：集中在 `TicketStatusEnum` 里，每个状态的"可去向"由一个 switch 返回 `EnumSet` 定义。

真实的流转表（对着代码抄的，不是我记忆里的简化版）：

| 当前状态 | 允许流转到 |
|---|---|
| `PENDING` 待派单 | `ASSIGNED`、`ESCALATED` |
| `ASSIGNED` 已派单 | `PROCESSING`、`CLOSED`、`ESCALATED` |
| `PROCESSING` 处理中 | `RESOLVED`、`CLOSED`、`ESCALATED` |
| `RESOLVED` 已解决 | `CLOSED`、`PROCESSING`（客户不满意可以退回重开） |
| `ESCALATED` 已升级 | `ASSIGNED`、`PROCESSING`、`CLOSED` |
| `CLOSED` 已关闭 | 无（终态） |

代码形状：

```java
public EnumSet<TicketStatusEnum> nextStates() {
    return switch (this) {
        case PENDING    -> EnumSet.of(ASSIGNED, ESCALATED);
        case ASSIGNED   -> EnumSet.of(PROCESSING, CLOSED, ESCALATED);
        case PROCESSING -> EnumSet.of(RESOLVED, CLOSED, ESCALATED);
        case RESOLVED   -> EnumSet.of(CLOSED, PROCESSING);
        case ESCALATED  -> EnumSet.of(ASSIGNED, PROCESSING, CLOSED);
        case CLOSED     -> EnumSet.noneOf(TicketStatusEnum.class);
    };
}
```

任何状态变更前先 `from.canTransitTo(to)`，非法就抛业务异常。

**注意**：`PENDING` 不在任何状态的去向里——待派单必须经过派单或抢单，
不能从别的状态"退回去"。`RESOLVED → PROCESSING` 是刻意留的：
客户说"问题还在"，可以把单退回处理中，而不是重新提一张新单。

**追问"为什么不用状态机框架（如 Spring StateMachine）"**：
6 个状态用框架是过度设计，一个 30 行的枚举就够，还不用学新东西。
如果状态到 20 个、有并行状态和嵌套状态，再上框架。

### B5. 待派单为什么不能直接关闭？

**答**：业务上是防止"客户提了单，没人处理就被直接关掉"。
如果允许，坐席看到不想要可以直接关，等于抹掉了这张单的存在。

必走流程是：待派单 → 派单/抢单 → 处理中 → 已解决 → 已关闭。
但客户端有关闭权（客户自己不想要了），所以 `close` 接口对客户开放，
只是状态机拒绝从 PENDING 直接关。

**这是个好问题，因为它考的是"权限和状态机是两件事"**——
客户有权限关闭，但当前状态不允许。

### B6. SLA 截止时间怎么算？

**答**：按（分类 + 优先级）查 `t_sla_rule`，取 `sla_minutes` 加到创建时间上。

```java
SlaRule rule = slaRuleMapper.selectOne(new LambdaQueryWrapper<SlaRule>()
        .eq(SlaRule::getCategory, category)
        .eq(SlaRule::getPriority, priority));
```

规则表有唯一索引 `uk_category_priority`，保证一个组合只有一条规则。

⚠️ **弱点**：现在规则是静态的，没考虑工作日历和节假日。
真实 SLA 要算"工作时间内 4 小时"，得排除晚上和周末。
我知道要怎么做（存工作时间段 + 用工作日历表算），但项目里没实现。

### B7. 查不到 SLA 规则怎么办？

**答**：`sla_deadline` 存 null，并打一条 warn 日志。

我当时的判断是：**宁可没有截止时间，也不要瞎猜一个数字**。
瞎猜会导致看板上的"SLA 达成率"是假的，而假指标比没指标更危险。

代码里注释写了这个取舍，可以当场翻给面试官看。

### B8. `t_idempotent` 这张表为什么单独存在？

**答**：存"这个请求我已经处理过了"，防止重复提交。

字段：`biz_key`（业务键，唯一索引）、`biz_type`、`expire_time`、`result_snapshot`。

流程：先用 `biz_key` 插入，靠唯一索引拦重复；插入成功才执行业务；
业务成功后把结果（工单 ID）回写到 `result_snapshot`。
重复请求命中唯一索引冲突，直接返回第一次的结果。

**为什么不用 Redis 做幂等**（重点，容易被追问）：
Redis 的 `setIfAbsent` 也是原子的，但它和数据库事务不同步——
业务事务回滚了，Redis 里的 key 还在，用户重试会被误判为"重复提交"。
数据库唯一索引和业务写入在同一个事务里，要么都成功要么都回滚。

## C. 认证与安全

### C1. JWT 是怎么工作的？

**答**：三段——Header、Payload、Signature，用 `.` 分隔。

我这个项目用 HS256（对称加密），密钥 32 字节以上，
Payload 里放 `userId`（subject）、`username`、`role`，有效期 120 分钟。

服务端不存 JWT 本身也能验：拿到 token 后用同一个密钥算一遍签名，比对一致就说明没被篡改。

**追问"JWT 和 Session 的区别"**：
Session 是服务端存状态、客户端只拿一个 ID；JWT 是状态在 token 里、服务端无状态。
JWT 适合横向扩展（不用共享 session），但代价是**无法主动失效**——这就是我为什么还要加 Redis。

### C2. 既然 JWT 是无状态的，为什么还要存 Redis？

**答**：因为要支持**主动失效**。

JWT 一旦签发，在过期前一直有效。用户点退出、密码泄露、员工离职，
这些场景都必须立刻断开，光靠 JWT 做不到。

我的做法：登录时把 token 存进 Redis（`auth:token:{userId}`，TTL 120 分钟），
每个请求除了验签，还要比对 Redis 里的值是否一致。退出登录就删掉这个 key。

**这样 JWT 就不再"无状态"了**——我知道。这是取舍：
我选择"能踢下线"，代价是每个请求多一次 Redis 读。

### C3. 那用 Redis 存 token，和用 Session 有什么区别？

**答**：本质差别不大，都是服务端存状态。但有两点不同：

一是存储介质。Session 默认在应用内存里，多实例要同步（粘性会话或共享存储）；
Redis 天然共享，多实例直接可用。

二是用途分离。Session 通常存整个用户对象；我只存 token 字符串用来比对，
用户信息从 JWT 里解出来，Redis 只承担"是否有效"这一个判断。

**这题答好了显得你懂原理而不是背概念。**

### C4. 同一个账号在另一台设备登录会怎样？

**答**：前一台会被踢下线。

因为 Redis 的 key 是 `auth:token:{userId}`，新登录会**覆盖**旧 token。
前一台设备再请求，比对 Redis 发现不一致，返回 401「登录已失效」。

这是"单端登录"，是取舍不是 bug。
售后坐席共用工作机，防止两人串号比支持多端更重要。

如果要支持多端，key 改成 `auth:token:{userId}:{deviceId}`，或者用 Set 存多个 token。

### C5. 密码怎么存的？

**答**：BCrypt，只存密文（长度 60，`$2a$10$` 前缀），不存明文。

BCrypt 有两个特点：自带随机盐（同一个密码每次加密结果不同），
并且计算慢（cost=10，约几十毫秒）——慢是故意的，让暴力破解成本变高。

我的做法是：初始化数据脚本里的密码是提前用 jshell 算好密文的，
明文根本没进过 SQL 文件，只在文档里写了演示密码。

**追问"为什么不用 MD5"**：MD5 太快，能每秒试上亿次，还容易撞彩虹表。

### C6. 怎么防止越权访问别人的工单？

**答**：两层。

第一层是查询收窄。列表接口按角色拼不同条件：
客户强制加 `creator_id = 当前用户`，这个条件由服务端从 token 取，**前端传什么都会被覆盖**；
坐席只能看本技能组的待派单 + 自己正在处理的；管理员看全部。

第二层是详情校验。`canView()` 方法，越权直接抛 `NotFoundException`，
**返回 404 而不是 403**——403 等于告诉攻击者"这个工单存在但你没权限"，
用 404 让他连存在性都探测不到。

**这是个安全设计题，答好加分很多。**

### C7. 内部备注客户能看到吗？

**答**：不能。回复表有 `is_internal` 字段，客户查询时服务端过滤掉 `is_internal=1` 的记录。

关键是：**客户提交回复时如果传 `internal=true`，服务端强制改成 0**。
前端可以作弊（改请求、用 Postman），权限判断必须在服务端。

验收脚本里专门有一条断言测这个（T8b）。

### C8. 接口被恶意调用怎么办？有做限流吗？

**答**：⚠️ **没做。这是当前项目的缺口。**

我准备了方案：Redis + 令牌桶，key 按用户维度
（`rate:limit:{userId}`，原子 INCR + 过期），或者用 Guava 的 RateLimiter 做单机限流。

没做的原因是——它是 Phase 2.2 的独立任务，而我优先把主流程跑通了。
如果现在要做，一个下午能加上。

**诚实承认没做，同时给出方案，比说"做了"被追问细节强一百倍。**

## D. 并发与事务（这个项目最值钱的部分）

### D1. 抢单怎么保证不会两个人同时抢到？

**答**：靠数据库乐观锁，不是靠锁框架。

核心 SQL：

```sql
UPDATE t_ticket
   SET handler_id = ?, status = 'PROCESSING', accept_time = ?, version = version + 1
 WHERE id = ?
   AND status = 'PENDING'
   AND handler_id IS NULL
   AND version = ?          -- 关键：读到的旧版本号
```

20 个请求并发时，MySQL 对那一行加行锁，请求排队。
第一个改成功，`version` 从 0 变 1；后面 19 个的 `AND version = 0` 不成立，
影响行数为 0，代码据此返回「已被其他坐席抢走」。

**一句话总结**：唯一性由数据库的 UPDATE 保证，锁只是让失败的请求早点返回。

### D2. 为什么不用悲观锁（SELECT ... FOR UPDATE）？

**答**：因为这个场景"冲突概率高但持锁时间可以极短"。

悲观锁会让 20 个请求全部排队持锁等待，第一个处理完才轮到第二个，
每个请求都要等前面所有请求结束，吞吐很低。

乐观锁只在 UPDATE 那一瞬间竞争，前面读数据不加锁，能并发读。
我这个场景写操作只有几条 SQL，失败代价低（重试或换单），适合乐观锁。

**反问**：如果不冲突的场景频繁出现，乐观锁会白做 version 检查；
如果冲突极高（100 抢 1），大量请求白跑 UPDATE 也浪费。
判断标准是：**冲突概率 × 重试代价**，而不是"哪个更先进"。

### D3. 为什么又实现了 Redis 锁？生产为什么不用？

**答**：为了做对比实验，也是面试时能讲清取舍。

两个版本都跑 20 并发，都是只有 1 个人成功。差别在耗时：

| | 乐观锁 | Redis 锁 |
|---|---|---|
| 第一轮 avg | 121 ms | 74.4 ms |
| 第二轮 avg | 137.2 ms | 29.8 ms |

Redis 锁平均更快，因为 19 个请求在 SETNX 阶段就被拒了，根本不碰数据库。

但生产我还是用乐观锁，原因是：
竞争范围只有一行数据，数据库行锁完全够；少一次网络往返；
少一个"必须存活"的外部依赖——Redis 挂了不该影响抢单。

**⚠️ 但要主动承认**：尾部延迟我测了两次结果不一致（一次 Redis 更高、一次更低），
20 个样本太小，我在文档里明确写了"尾部延迟不下结论"。
面试官听到这种自我限制，反而更信你其他结论。

### D4. Redis 分布式锁怎么实现的？有什么坑？

**答**：三个必备要素。

```java
String token = UUID.randomUUID().toString();
Boolean got = redis.opsForValue().setIfAbsent(key, token, Duration.ofSeconds(30));
if (!got) throw new BizException("手慢了");
try {
    doAccept(id, userId, "REDIS_LOCK");
} finally {
    redis.execute(UNLOCK_SCRIPT, List.of(key), token);
}
```

释放脚本（Lua）：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

四个坑：

1. **必须设过期时间**。不设的话，持锁进程崩溃后锁永远不释放，这张单再没人能抢。
2. **释放必须比对 value**。如果先 get 再 del，两步之间锁可能过期并被别人拿走，
   你的 del 就删了别人的锁。用 Lua 保证"判断和删除"是一个原子操作。
3. **拿到锁还要二次校验**。你拿到锁之前，前一个持锁者可能刚处理完并释放。
   所以 `doAccept` 里仍然重新读库检查状态。
4. **业务耗时必须小于锁过期时间**。抢单是毫秒级，30 秒很宽松；
   如果锁的是慢操作（调第三方接口），要考虑续期（watchdog）。

### D5. 幂等是怎么做的？连发 5 次会怎样？

**答**：只建 1 条。

客户端每次提交带一个 `requestId`（前端用 `crypto.randomUUID()` 生成，
提交失败重试时**复用同一个**）。服务端在同一个事务里：

1. 先用 `biz_key = "CREATE_TICKET:" + requestId` 插 `t_idempotent`
2. 唯一索引冲突 → 说明是重复请求 → 查出 `result_snapshot` 直接返回第一次的结果
3. 插入成功 → 执行业务 → 把工单 ID 回写进 `result_snapshot`

验收脚本里有这条断言：同一个 requestId 连发 5 次，返回同一个工单号，库里只有 1 行。

### D6. 为什么幂等不放在 Redis？

**答**：因为 Redis 和数据库事务不同步。

业务事务回滚了，Redis 的 key 还在，用户重试会被当成重复请求，
但其实第一次根本没成功——用户就卡死了。

数据库唯一索引和业务写入在同一个事务里，要么都成功要么都回滚，不存在中间态。

**这也解释了为什么"看起来更快"的方案不一定对。**

### D7. 事务边界怎么划的？

**答**：方法级 `@Transactional(rollbackFor = Exception.class)`，
一个业务动作一个事务。

比如转派：改工单状态 + 写派单记录 + 写流转日志，
三张表的写入必须一起成功或一起失败，否则会出现"日志说转派了但工单没变"。

`rollbackFor = Exception.class` 是必须写的——Spring 默认只对 RuntimeException 回滚，
受检异常不回滚，这是个经典坑。

⚠️ **弱点**：我没做分布式事务。现在所有写入在同一个库，本地事务够用。
如果以后拆服务，得用本地消息表或 Seata——但那是拆服务以后的事，现在加是过度设计。

### D8. 如果 UPDATE 返回 0 行，怎么判断是"被抢了"还是"工单不存在"？

**答**：先查一次再更新，所以两种情况分开处理。

```java
Ticket t = requireTicket(id);        // 不存在 → 404
// 状态不是 PENDING 或已有处理人 → 直接失败，不用 UPDATE
LambdaUpdateWrapper ... .eq(Ticket::getVersion, t.getVersion());
int rows = ticketMapper.update(null, uw);
if (rows == 0) {                     // 到这里只可能是并发抢走了
    throw new BizException("手慢了，这单已被其他坐席抢走");
}
```

**关键**：UPDATE 之前先做"廉价校验"（查一次库），
把"不存在""状态不对"这些情况提前拦掉，
剩下的 `rows == 0` 就一定是并发冲突，错误信息才准确。

### D9. 多个状态字段同时改了，会有脏写吗？

**答**：抢单这条路径不会，因为 `version` 是唯一的判断依据，
而且 UPDATE 的条件里同时带了 `status='PENDING'` 和 `handler_id IS NULL`——
三个条件只要有一个不成立，就改不动。

但我要承认：**转派（transfer）和关闭（close）没有走乐观锁**，
直接 `updateById`。理论上两个人同时转派会互相覆盖。
我的判断是这两个操作频率低、冲突可接受（最坏结果是被后一个人覆盖，能查日志追溯），
但如果要严格，应该给所有状态变更都加 version 条件。

⚠️ **主动说出这个不彻底的地方，比被问出来好。**

### D10. 如果 20 个并发不是抢单，而是 20 个人同时创建工单，会有问题吗？

**答**：单号可能有重复风险，我已处理。

单号是 `TK + 日期 + 6 位序号`，序号来自 Redis `INCR`（原子操作），不会重。
如果 Redis 挂了，降级成时间戳尾数，**可能重号**——
但 `ticket_no` 有唯一索引，重复的会插入失败，用户重试即可。

**取舍原则**：宁可偶发失败并重试，也不能因为 Redis 挂了导致全站不能提单。

## E. 数据库与索引

### E1. 13 个索引，都是为什么建的？

**答**：每个索引都对应一条真实查询，没有"以防万一"建的。

| 表 | 索引 | 对应查询 |
|---|---|---|
| t_user | `uk_username` | 登录按用户名查 |
| t_user | `idx_role_status(role,status)` | 自动派单选"在线坐席" |
| t_ticket | `uk_ticket_no` | 单号唯一 + 按单号查 |
| t_ticket | `idx_skill_status_time(skill_group,status,create_time)` | **坐席抢单大厅**：本组 + 待派单 + 按时间倒序 |
| t_ticket | `idx_handler_status(handler_id,status)` | 坐席"我的在处理" |
| t_ticket | `idx_sla_deadline(sla_deadline)` | SLA 超时扫描（Phase 5） |
| t_ticket | `idx_creator_time(creator_id,create_time)` | **客户"我的工单"**：按人 + 时间倒序 |
| 三张流水表 | `idx_ticket_time(ticket_id,create_time)` | 详情页拉日志/回复/派单记录 |
| t_sla_rule | `uk_category_priority` | 算 SLA 截止时间 |
| t_idempotent | `uk_biz_key` | 幂等拦截（唯一性） |
| t_idempotent | `idx_expire_time` | 定期清理过期记录 |

判据：有查询 + 有选择性 + 排序字段在索引里。

### E2. 最左前缀原则，举个你项目里的例子

**答**：`idx_skill_status_time(skill_group, status, create_time)`。

- `WHERE skill_group=? AND status=? ORDER BY create_time DESC` → 三列全用上，排序也走索引，不需要 filesort ✅
- `WHERE status=?` → 用不上（跳过了最左列 skill_group）❌
- `WHERE skill_group=? ORDER BY create_time` → 只用到第一列，排序不能靠索引（因为 status 断了）⚠️

**我把 create_time 放在最后就是因为查询总是"先按组、再按状态过滤、最后按时间排序"**，
顺序反了索引就用不上排序能力。

### E3. 深分页为什么慢？怎么优化？

**答**：`LIMIT 100000, 20` 的代价是 MySQL 要扫描并丢弃前 10 万行。

两种优化：

一是**游标（keyset）分页**：`WHERE id < 上一页最后一个id ORDER BY id DESC LIMIT 20`，
利用索引直接定位，不扫丢弃行。缺点是只能"下一页"不能跳页。

二是**延迟关联**：先在索引上取 20 个主键，再回表
`SELECT * FROM t JOIN (SELECT id FROM t ORDER BY create_time DESC LIMIT 100000,20) x ON t.id=x.id`。

⚠️ **我这个项目只做了最土的一条**：分页插件设了 `maxLimit=100`，
单页最多 100 条，超深页码直接拒绝。真正的游标分页排列 Phase 6。

### E4. 怎么验证索引真的生效了？

**答**：`EXPLAIN`，看几个关键列。

- `type`：最好到 `ref` / `range`，出现 `ALL` 就是全表扫描
- `key`：实际用了哪个索引，null 就是没用
- `rows`：预估扫描行数，越小越好
- `Extra`：出现 `Using filesort` 说明排序没走索引，`Using temporary` 说明用了临时表

我在 `docs/index-design.md` 里给每个索引写了 EXPLAIN 的期望值，
但没有跑过真实数据量下的对比——⚠️ 现在库里只有几十条数据，
优化器可能直接全表扫描，看不出索引价值。这是我要补的（Phase 6）。

### E5. utf8mb4 和 utf8 的区别？为什么要定 DATETIME(3)？

**答**：MySQL 的 `utf8` 其实是 utf8mb3，最多 3 字节，存不了 emoji 和部分生僻字。
`utf8mb4` 才是真 UTF-8。工单描述里用户很可能打 emoji，用 utf8 会插入失败或乱码。

`DATETIME(3)` 是毫秒精度。工单流转日志可能同一秒内产生多条（比如抢单同时写日志），
秒级精度会导致"两条记录时间一样"，排序和排查都难。

另外没选 `TIMESTAMP`：它有时区转换、2038 年问题；`DATETIME` 存的就是字面时间，
配合统一 `Asia/Shanghai` 更可控。

### E6. 查询条件很多（六条件），索引怎么建？

**答**：我不打算给六个条件建一个复合索引——那不可能覆盖所有组合。

实际策略：

- **必带的、选择性高的**做索引前缀：客户查自己的单一定是 `creator_id`，
  坐席查一定是 `handler_id` 或 `skill_group`——这两个是索引的第一列
- **状态**做第二列，因为状态值域小（6 个），但组合后选择性明显提升
- **关键字模糊搜索** `LIKE '%xxx%'` 用不上索引。我知道这会慢，
  正确做法是上 ES 或者 MySQL 全文索引，但我没做——⚠️ 数据量小的时候可以接受

## F. Redis（这个项目里 Redis 只干两件事）

### F1. Redis 在你项目里用来做什么？

**答**：两件事，都写进 `docs/redis-usage.md` 了。

一是存 JWT 令牌，实现可撤销登录态（`auth:token:{userId}`，TTL 120 分钟）。
二是生成工单单号的序号（`ticket:no:{yyyyMMdd}`，`INCR` 原子自增，48 小时过期）。

另外还实现了一个抢单分布式锁，但生产没用，只做对比实验。

**业务数据一条都没进 Redis**，全在 MySQL。

### F2. 单号为什么要用 Redis 不用数据库自增？

**答**：三个原因。

一是**可读**。`TK20261106 000001` 一眼能看出日期和第几单，
数据库自增只能得到 `1、2、3`，跨天不会归零。

二是**按天归零**。我用日期做 key 的一部分，第二天自动从 1 开始，
旧 key 48 小时后自动过期，**不用写清理任务**。

三是**并发安全**。`SELECT MAX(no)+1` 在并发下会重号（两个请求读到同一个 max），
Redis 的 `INCR` 是单线程原子操作，不可能重复。

### F3. Redis 挂了会怎样？

**答**：两个影响，都有预案。

登录态：所有 token 校验失败，用户被登出，重新登录即可。
影响是"要重新登录"，不是"数据丢了"。

单号生成：代码里有降级——捕获异常后返回时间戳尾数，可能重号，
但 `ticket_no` 有唯一索引，重复会插入失败，用户重试就好。

**原则**：宁可偶发失败，不可全站不可用。

### F4. Redis 内存会不会爆？

**答**：每个 token 约 200 字节，1 万在线用户约 2MB；
单号 key 一天一个，48 小时最多两个。

容器配了 `--maxmemory 200mb --maxmemory-policy allkeys-lru`，
真到上限会按 LRU 淘汰——最坏情况是部分用户被登出，不会 OOM。

⚠️ 但 `allkeys-lru` 有个隐患：它可能淘汰掉还在用的 token。
更稳妥的做法是给 token 单独用 `volatile-lru`（只淘汰设了过期时间的 key），
或者分开两个 DB。这个我知道，但没改。

### F5. 你项目里为什么不做缓存（比如缓存工单列表）？

**答**：因为不该做。

工单列表要求强实时——状态一变，客户和坐席必须立刻看到。
加缓存就要处理"什么时候失效"，一致性成本高于收益。

而且查询都走了索引，单表几十万行的量级下 MySQL 完全够。
**缓存是用来解决"读多写少 + 能容忍延迟"的，不是用来显得技术栈丰富的。**

如果真要做，我会缓存的不是列表，而是**统计看板**——那个是聚合查询，
允许分钟级延迟，命中率也高。

### F6. 缓存穿透、击穿、雪崩分别是什么？

**答**：虽然这个项目没用到业务缓存，概念我清楚。

- **穿透**：查一个不存在的数据，缓存和数据库都没有，每次请求都打到库。
  解法：缓存空值 + 短期 TTL，或用布隆过滤器。
- **击穿**：某个热点 key 刚好过期，大量请求同时打到库。
  解法：互斥锁（只让一个请求去重建），或逻辑过期（不设 TTL，值里存过期时间）。
- **雪崩**：大量 key 同时过期，或 Redis 整个挂了。
  解法：过期时间加随机抖动；Redis 集群 + 降级。

**我这个项目里其实已经踩过一个小号的雪崩**：
所有 token 的 TTL 都是 120 分钟，如果 Redis 重启，所有人同时被登出。
真实系统会让 TTL 在一个区间内随机，避免同时失效。

## G. 接口设计与工程化

### G1. 统一返回结构为什么这么设计？

**答**：`{ code, message, data, traceId }`。

- `code`：0 表示成功，非 0 是业务错误码（1000 业务失败、401 未登录、403 无权限、404 不存在）
- `data`：业务数据，失败时为 null
- `traceId`：每个请求生成一个，同时写进日志和响应头

**为什么 HTTP 状态码也要改**：这是我在项目里踩过的坑（事故 H）。

一开始所有异常都返回 HTTP 200 + body 里写 code=404。
后来发现这样接口成功率报表永远是 100%，线上真出问题也发现不了。
现在 401/403/404 都会返回真实 HTTP 状态码，body 里仍然带 code 保持前端兼容。

### G2. traceId 怎么做？有什么用？

**答**：一个 Filter 在请求进来时生成 UUID（或从 header 里取），
放进 MDC，同时塞进响应头 `X-Trace-Id`；日志格式里带 `%X{traceId}`。

排查时用户说"我刚才报错了"，让他把 traceId 发过来，
`grep traceId logs/app.log` 就能看到这个请求的完整链路。

⚠️ **弱点**：现在是单服务，traceId 只在一个进程内有用。
微服务下要用 SkyWalking 或 Sleuth 做链路透传，我还没做过。

### G3. 参数校验怎么做的？

**答**：Bean Validation 注解 + 全局异常处理。

DTO 上写 `@NotBlank`、`@Size(max=200)`，Controller 参数加 `@Valid`，
校验失败 Spring 抛 `MethodArgumentNotValidException`，
全局异常处理器统一转成 400 + 第一条错误信息（用逗号拼所有错误更好）。

验收脚本里有一条断言专门测空密码返回 400。

### G4. 数据库变更加了字段，线上怎么迁移？

**答**：用 Flyway，脚本入库，启动时自动执行。

`V1__init_schema.sql` 建表，`V2__init_demo_data.sql` 初始化数据。
Flyway 会在 `flyway_schema_history` 表里记录已执行的版本，
不会重复执行，也不会让不同环境的表结构不一致。

**关键优势**：clone 下来直接启动，表就建好了，不需要"照着文档手动建表"。
面试官如果现场跑你的项目，这一步能省他 20 分钟——这也是一种工程素质。

⚠️ 我知道 Flyway 在生产有个坑：`V` 开头的脚本一旦执行就不能改（校验和不匹配会启动失败），
要改结构必须加新版本号 `V3__`。我项目里还没遇到，但知道规矩。

### G5. 日志怎么打的？敏感信息怎么处理？

**答**：用 Slf4j，分级打。

- 正常业务变更：`info`，带关键参数（ticketId、userId、状态变化）
- 可预期的失败（业务异常）：`warn`，不打堆栈（避免日志刷爆）
- 真正的异常：`error` + 堆栈

敏感信息：密码从不出现在日志里（`UserVO` 里根本没有 password 字段，
实体类也不参与日志打印）。JWT 只在调试时打前 20 个字符。

⚠️ 我没做日志脱敏框架，如果以后要打手机号、身份证，得自己加脱敏工具。

### G6. 你的验收脚本为什么不用 JUnit？

**答**：⚠️ 这是个真实的取舍，也是不足。

我当时的目标是"端到端验证真实链路"——起真实服务、连真实 MySQL 和 Redis、
用真实 HTTP 请求打接口。这种测试用 PowerShell 脚本更直接，不用配 Spring Test 上下文。

代价是：不能进 CI、不能 mock、断言失败时定位不如单测精确。

**正确做法是两者都要**：单元测试覆盖业务逻辑分支（SLA 计算、状态机非法流转），
接口脚本覆盖端到端链路。我目前只有后者。

### G7. 如果让你加 CI，你会怎么做？

**答**：GitHub Actions，三个 job 并行：

1. 后端编译 + 单元测试（`mvn verify`）
2. 前端构建（`npm ci && npm run build`）
3. 起 MySQL/Redis 容器（services 或 docker-compose），跑接口验收脚本

第三个 job 是关键，也是最麻烦的——要在 CI 里等容器健康检查通过。

⚠️ 没做过。我知道流程，但没在真实 CI 里跑通过。

## H. 前端与联调

### H1. 前端怎么处理 401？

**答**：axios 响应拦截器统一处理。

收到 401 → 清掉本地 token 和用户信息 → 跳登录页 → 记下当前路由，
登录后跳回来。多个请求同时 401 时要有"只跳一次"的保护，否则会跳好几次。

### H2. 前端怎么按角色显示菜单？

**答**：路由 `meta.roles` 标注哪些角色能进，侧边栏按当前角色过滤菜单。
路由守卫里再校验一次（防止直接敲 URL），没权限跳 403 页。

**但真正的权限必须在后端**——前端过滤只是体验，不是安全边界。
后端每个接口都有 `@RequireRole` 注解 + 拦截器校验。

### H3. 前端怎么知道后端改了什么？

**答**：Swagger UI（`/swagger-ui.html`），由 springdoc 从注解自动生成。
我每个接口都写了 `@Operation` 说明，DTO 字段有 `@Schema` 描述。

另外前端接口层集中在 `src/api/` 一个目录，改一个地方就行。

## I. 被问住的时候怎么办

**三条原则**：

1. **不知道就说不知道，然后说你会的邻近知识**。
   "分布式事务我没做过，但我知道本地事务的边界怎么划，也知道 Seata 大致解决什么问题。"
   编造比不会更致命——面试官一追问细节就崩。

2. **把问题拉到你的强项上**。
   问"你们怎么做灰度发布"→"我没做过灰度发布，这个项目是单机部署。
   但我做过接口版本兼容的考虑，比如新增字段不影响老前端……"

3. **主动说不完美的部分**。
   "这块我做得比较粗，只考虑到了 X，没考虑 Y。"
   这比声称完美可信得多，而且面试官会认为你**知道自己的边界**。

## K. 三条追问链（面试官最可能的深挖路径）

### 链 1：从"抢单"到"分布式"

> 问：抢单怎么做的？
> 答：乐观锁，`WHERE version=?`，影响行数 0 就失败。
>
> 追问：如果服务部署 3 个实例呢？
> 答：不影响，乐观锁靠数据库，不依赖进程。
>
> 追问：那什么情况进程锁会失效？
> 答：多实例部署、或者用了多线程池。`synchronized` 只锁住当前 JVM。
>
> 追问：那什么时候必须用分布式锁？
> 答：跨服务、跨数据库的互斥。比如下单要同时扣库存、扣优惠券、加积分，
> 三个操作在不同服务里，数据库行锁管不到这个范围。

### 链 2：从"JWT"到"会话管理"

> 问：JWT 怎么用？
> 答：HS256 签名，claims 放 userId/username/role，120 分钟过期。
>
> 追问：那用户改密码后，旧 token 还能用吗？
> 答：不能，因为我存了 Redis，改密码时删掉 key 就行。⚠️ 但**我现在没实现改密码接口**，
> 这是缺的。逻辑上就是在改密码事务里 delete 那个 key。
>
> 追问：多端登录怎么支持？
> 答：key 加设备维度，或者用 Set 存多个 token。

### 链 3：从"索引"到"SQL 优化"

> 问：你这个索引为什么这么建？
> 答：`(skill_group, status, create_time)`，对应抢单大厅的查询：本组 + 待派单 + 时间倒序。
>
> 追问：如果查询变成"按优先级排序"呢？
> 答：现在索引就没法覆盖排序，会 filesort。要么加 `(skill_group, status, priority, create_time)`，
> 要么接受小数据量的排序开销。加索引前要看查询频率——写多读少的表加索引要谨慎。
>
> 追问：那你怎么判断该不该加？
> 答：看执行计划 + 看慢查询日志里这条 SQL 的调用频率和耗时占比。
> 具体数字我这里没有，因为这个项目数据量太小，还没跑出慢查询。
