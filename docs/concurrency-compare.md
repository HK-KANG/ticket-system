# 抢单并发方案对比：乐观锁 vs Redis 分布式锁

> 实测环境：本机（Windows 11 + WSL2），Spring Boot 3.5 单实例，MySQL 8.4 与 Redis 8 跑在 WSL 的 Docker 里。
> 压测脚本：`scripts/verify-concurrency.ps1`（20 个并行请求打同一张工单）
> 实测时间：2026-11-06 23:0x

---

## 一、结论先说

**这个项目用乐观锁，不用 Redis 锁。**

原因不是"Redis 锁不好"，而是抢单这个场景不需要它：
- 竞争只发生在**同一行数据**上，数据库自己的行锁就够
- 少一次 Redis 往返，也少一个必须存活的外部依赖
- Redis 锁的全部价值（跨服务互斥、提前拦截）在这个场景里都用不上

Redis 锁的版本仍然保留在代码里（`/api/ticket/{id}/accept-lock`），作为面试时的对比材料。

---

## 二、实测数据（20 并发抢同一张工单）

| 指标 | 版本 A：乐观锁 | 版本 B：Redis 锁 |
|---|---|---|
| 成功次数 | **1** | **1** |
| 失败次数 | 19 | 19 |
| 平均响应 | 121 ms | **74.4 ms** |
| 最快 | 28 ms | **12 ms** |
| P95 | **222 ms** | 295 ms |
| 最慢 | **222 ms** | 295 ms |

**一致性结果（两版本相同）**
- 两张工单最终状态都是 `PROCESSING`，`handler_id` 都只有一个值
- `t_ticket_log` 里 ACCEPT 记录各 **1 条** —— 不存在"两人同时处理一张单"

## 四、为什么两者都只有 1 个成功

这是本次实验最重要的认知：**保证唯一性的不是锁，是数据库。**

乐观锁版本的 SQL（MyBatis-Plus 生成）：

```sql
UPDATE t_ticket
   SET handler_id = ?, status = 'PROCESSING', accept_time = ?, version = version + 1
 WHERE id = ?
   AND status = 'PENDING'
   AND handler_id IS NULL
   AND version = ?          -- 关键：带上读到的旧版本号
```

20 个请求并发执行时：MySQL 对这一行加行锁，请求排队。第一个执行成功，`version` 从 0 变 1；
后面 19 个请求的 `AND version = 0` 不再成立，影响行数为 0，代码据此返回"已被他人抢走"。

Redis 锁版本里，唯一性同样由这条 UPDATE 保证——锁只是让 19 个请求提前失败，
不必挤到数据库前面排队。

**这也意味着：即使 Redis 锁的实现有 bug（比如锁过期时间设得太短、或者释放时机错了），
数据仍然不会出现"两个人同时处理一张单"。这是"数据库兜底"的价值。**

## 五、为什么 Redis 锁版平均更快、但 P95 更慢

| | 乐观锁 | Redis 锁 |
|---|---|---|
| 平均 121 ms | 20 个请求全部打到数据库，19 个在行锁上排队等第一个提交 | — |
| 平均 74 ms | — | 19 个请求在 SETNX 阶段就被拒（一次 Redis 往返），根本不碰数据库 |

所以平均耗时 Redis 锁版明显更低：**失败得更早**。

但 P95 反而更高（295 vs 222），原因是尾部：
- 拿到锁的那个请求要多付两次 Redis 往返（SETNX + Lua 释放）
- 20 个线程同时打 Redis，连接池（max-active 8）出现排队
- 释放锁的 Lua 脚本在 finally 里执行，即使业务失败也要走一次

**一句话：Redis 锁把平均延迟降低了，把尾部延迟抬高了。**

## 六、什么情况该换 Redis 锁

| 场景 | 建议 |
|---|---|
| 同一行数据的并发修改（本项目抢单） | 乐观锁。数据库行锁最轻，无需外部依赖 |
| 跨多张表 / 跨多个服务的互斥（下单扣库存 + 优惠券 + 积分） | Redis 锁。数据库行锁管不到这个范围 |
| 冲突概率极高（100 个请求抢 1 个名额） | 可以用锁提前拦截，避免 100 个请求打到数据库 |
| 需要限流、幂等组合控制 | Redis（但幂等的最后一道防线仍应是唯一索引） |
| 高并发写同一行且失败代价高 | 考虑排队（MQ 串行消费），而不是加锁 |

## 七、Redis 锁的四个必须做对的细节（本项目都做了）

1. **锁必须有过期时间**
   `setIfAbsent(key, token, 30s)`。不加过期，持有锁的进程崩溃后这把锁永远不释放，
   这张工单就再也没人能抢。

2. **释放必须比对 value**
   释放用 Lua：`if redis.call('get',KEYS[1]) == ARGV[1] then return redis.call('del',KEYS[1]) end`。
   如果先 get 再 del，两步之间锁可能刚好过期并被别人拿走，你的 del 就删了别人的锁。

3. **锁内要二次校验状态**
   拿到锁不等于状态还是待派单——你拿到锁之前，前一个持锁者可能刚刚处理完并释放。
   所以 `doAccept` 里仍然重新读了一次工单并检查状态。

4. **业务超时 < 锁过期时间**
   锁 30 秒过期，业务必须在这之前结束。本项目抢单只是几条 SQL，毫秒级，不存在这个问题；
   如果要锁住一个慢操作（比如调第三方接口），就得考虑续期（watchdog）。

## 八、面试怎么讲这一段

被问"你怎么保证抢单不会两个人同时抢到"时的回答顺序：

1. 先说结论：**靠数据库的乐观锁，不靠锁框架**
2. 给出那条 UPDATE 和 `version` 条件，说明影响行数为 0 就是抢失败
3. 说明为什么不用悲观锁（`SELECT ... FOR UPDATE`）：高频短事务，排队持锁吞吐更低
4. 主动说我做了对比实验：另外实现了 Redis 分布式锁版本，20 并发下两者都只有 1 个成功，
   但 Redis 版平均更快、P95 更慢，因为失败得更早、但成功路径多两次 Redis 往返
5. 收尾说清边界：如果业务跨多个服务，数据库行锁管不到，那时才需要 Redis 锁；
   而且即使有锁，最终一致性仍要靠数据库约束兜底

这一段能同时展示：并发正确性、性能权衡、以及"不迷信中间件"的判断力。

## 九、复现方法

```bash
# 后端需在 127.0.0.1:8080 运行，且 ticket 技能组有在线坐席
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\verify-concurrency.ps1
```

脚本会：创建工单 → 20 并行抢单（两个版本各一轮）→ 校验只有 1 个成功、日志只有 1 条 →
测试自动派单与标记解决 → 打印实测数据表。

注意：脚本会在数据库留下测试工单（标题以 `concurrency experiment` 开头），
需要清理时执行 `docs/操作日志.md` 第十四节里记录的清理 SQL。
